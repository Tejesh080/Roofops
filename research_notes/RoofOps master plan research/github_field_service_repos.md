## Key question 1: Which open-source field-service / job-management / contractor-CRM projects exist, and which are serious versus toys?

### Takeaway
There is no serious (>500 stars, active in 2025-26) open-source project dedicated to trades/field-service job management on GitHub; the only one with real traction is the Odoo community add-on suite OCA/field-service (203 stars, pushed 28 Oct 2026). Everything else in the niche is under 30 stars. The "serious" code lives in general ERP/CRM platforms (Odoo, ERPNext, Dolibarr, Twenty, Frappe CRM, Invoice Ninja, Atomic CRM) that cover quoting/invoicing but not crews, site visits or Xero.

## Key question 2: How do the serious projects model the job lifecycle and status transitions, and do any enforce transitions in the database?

### Takeaway
Serious platforms model status as application-level enums or user-configurable "stages", with transition rules in application code (Frappe's docstatus machine, ERPNext's computed `status_map`, Odoo's fixed `state` + configurable `stage_id`, Dolibarr integer constants). Only tiny projects put the state machine in Postgres (FieldOpt's PL/pgSQL transition table; Docketworks' CHECK constraint on status values); none of the serious ones use Postgres triggers or state tables.

### Cited Findings
- Frappe/ERPNext docstatus is a strict three-state machine (0 Draft, 1 Submitted, 2 Cancelled); allowed moves are Draft→Draft (save), Draft→Submitted (submit), Submitted→Submitted (update after submit), Submitted→Cancelled (cancel); "everything else throws". — [Frappe docs: docstatus](https://docs.frappe.io/framework-git/doctypes/docstatus)
- ERPNext derives the human status from a `status_map` evaluated in Python: Sales Order statuses are Draft; "To Deliver and Bill" (`per_delivered < 100 and per_billed < 100 and docstatus == 1`); "To Bill"; "To Deliver"; "To Pay" (`advance_payment_status == 'Requested'`); "Completed" (`per_delivered >= 100 ... and per_billed >= 100`); Cancelled (`docstatus==2`); Closed; On Hold. Quotation: Draft/Open/Lost/Partially Ordered/Ordered/Cancelled. Purchase Order: Draft/To Bill/... — [erpnext/controllers/status_updater.py](https://github.com/frappe/erpnext/blob/develop/erpnext/controllers/status_updater.py)
- Frappe Workflow DocType rows map each workflow state to a `doc_status` of 0/1/2 and each transition to (source state, action, target state, allowed role, optional condition); the engine sets the state field then saves/submits/cancels. (Secondary sources summarising Frappe docs.) — [openskillindex: frappe-core-workflow](https://openskillindex.com/skills/openaec-foundation-frappe-claude-skill-package-frappe-core-workflow); a forum thread reports a Submitted→Submitted workflow transition rejected with "Illegal Document Status" — [discuss.frappe.io #62223](https://discuss.frappe.io/t/workflow-issue-error-when-transitioning-from-submitted-state/62223)
- Beveren FSM Service Order `status` is a Select with options "Open, Scheduled, Dispatched, In Progress, Review, Completed", flagged `read_only`, `hidden`, `allow_on_submit` (i.e. derived by code, not user-set); Service Appointment: "Open, Scheduled, Dispatched, In Progress, Completed, Cancelled"; Service Request: "Open, Quotation, Converted, Due Soon, Overdue, On Hold, Closed". — [service_order.json](https://github.com/Beveren-Software-Inc/Field_Service_Management/blob/HEAD/beveren_fsm/field_service_management/doctype/service_order/service_order.json); [service_appointment.json](https://github.com/Beveren-Software-Inc/Field_Service_Management/blob/HEAD/beveren_fsm/field_service_management/doctype/service_appointment/service_appointment.json); [service_request.json](https://github.com/Beveren-Software-Inc/Field_Service_Management/blob/HEAD/beveren_fsm/field_service_management/doctype/service_request/service_request.json)
- OCA fieldservice: `fsm.order.stage_id` is a Many2one to `fsm.stage`; stages have `sequence`, `is_closed`, `is_default`, `fold`, `custom_color`, `require_signature` and a `stage_type` Selection of order/equipment/location/worker; `action_complete()` and `action_cancel()` simply write `stage_id` to the `fieldservice.fsm_stage_completed` / `fsm_stage_cancelled` records; `write()` has a hook when the completed stage is reached; there is no transition matrix in the core model. Users configure stages under Field Service > Configuration > Stages. — [fsm_order.py](https://github.com/OCA/field-service/blob/19.0/fieldservice/models/fsm_order.py); [fsm_stage.py](https://github.com/OCA/field-service/blob/19.0/fieldservice/models/fsm_stage.py); [fieldservice README.rst](https://github.com/OCA/field-service/blob/19.0/fieldservice/README.rst)
- OCA adds guard/side-effect modules: `fieldservice_stage_validation` — "Validate input data when reaching a Field Service stage"; `fieldservice_stage_server_action` — "Execute server actions when reaching a Field Service stage"; `fieldservice_sign` — "Customer signature capture and document signing on FSM orders". — [OCA/field-service README](https://github.com/OCA/field-service/blob/19.0/README.md)

- rrios4/roofing-webapp: statuses are lookup tables (`invoice_status`, `quote_status`, `quote_request_status`, planned `project_status`) and money fields are maintained by Postgres trigger functions (`update_invoice_totals`, `update_quote_totals`, `update_invoice_amount_due_on_payment`). — [roofing-webapp README schema](https://github.com/rrios4/roofing-webapp)

### Inferences
- The common pattern in mature systems is two layers: a small fixed lifecycle enum (Frappe docstatus; Odoo `state`; Dolibarr constants) plus a user-configurable pipeline/stage for Kanban. RoofOps' enquiry→quote→job→invoice chain maps naturally to that split: a fixed enum per entity, with Airtable-visible "stage" labels layered on top.
- ERPNext's approach of computing status from measurable facts (per_delivered, per_billed, docstatus) rather than storing it as a free choice is the most robust model found and is cheap to copy as a Postgres generated column or view.
- No serious project enforces transitions with Postgres triggers; the two that put rules in the DB (FieldOpt RPC functions, Docketworks CHECK constraint) are solo projects. A trigger-enforced transition table in RoofOps would be unusual but not contradicted by anything found.

### Gaps

- Odoo Enterprise `industry_fsm` task statuses could not be inspected (private repo).

## Key question 4: Any open-source projects pairing Airtable (or a no-code DB) with Postgres as the canonical store, and how they handle two-way sync and echo loops?

### Takeaway
No open-source project implements two-way Airtable↔Postgres sync with documented echo-loop handling; the open-source tools are one-way Airtable→Postgres replicators (airtable_pg_sync, SyncAirtablePostgres), and two-way sync exists only as hosted products (Whalesync, StackSync, Bracket). The best open-source reference for loop prevention is ledgerbridge's QBO engine (origin tagging via SyncToken plus state hashes), which is directly transferable.

### Cited Findings
- benurwin/airtable_pg_sync: 3 stars, MIT, Python, last push 2024-09-19; replicates "an entire Airtable base in a Postgres schema" in one-off or perpetual mode, the latter listening to Airtable webhooks (scopes `data.records:read`, `schema.bases:read`, `webhook:manage`); creates a table named by the Airtable table id with field-id column names plus a view with human names "for applications requiring robustness with respect to column name changes". One-way only. — [airtable_pg_sync README](https://github.com/benurwin/airtable_pg_sync); [PyPI airtable-pg-sync](https://pypi.org/project/airtable-pg-sync/0.0.46)
- NanoNets/SyncAirtablePostgres: 3 stars, MIT, Python, last push 2021-02-13, "Utility to sync tables from Airtable to Postgres" (one-way). — [SyncAirtablePostgres](https://github.com/NanoNets/SyncAirtablePostgres)
- etischenkoown/airtable-rest-graphql-postgres: 0 stars, Apache-2.0, last push 2018-10-31, "Drop-in replacement for Airtable API with two-way sync backed by PostgreSQL" (abandoned). — GitHub search "airtable postgres sync".

- Whalesync markets "two way, real-time sync" between Postgres and Airtable with field mapping, backfill and automatic rate-limit retries, but its pages conflict on whether the Postgres connector is live, and none describe loop or conflict handling; StackSync and Bracket are also hosted. — [Whalesync Postgres↔Airtable](https://whalesync.com/sync/postgres-airtable); [StackSync Airtable + PostgreSQL](https://www.stacksync.com/integrations/airtable-and-postgresql); [Airtable community thread](https://community.airtable.com/t5/other-questions/connecting-airtable-base-to-postgresql-via-ssh-tunnel/m-p/41289)
- ledgerbridge's loop prevention (QBO, not Airtable): inbound echoes are detected by comparing the provider's `SyncToken` with the one recorded on the link row; internal echoes are detected by a state hash; "Edit in both → a conflict opens on the Conflicts queue (neither side clobbered)"; a reconciler "refetches both sides and, when a version/hash has moved past what we last synced, enqueues a synthetic event into the same idempotent outbox". — [ledgerbridge README](https://github.com/Qweffy/ledgerbridge)
- Turnout's offline crew packets merge "Three-way per field": base (as exported), office, crew; "Crew equals base: nothing. Office equals base: the crew's value is taken. Office equals crew: nothing. Otherwise the person chooses office or crew. Checklist items merge per item." — [turnout README](https://github.com/wjwhitmire/turnout)
- Open-source Airtable alternatives that are Postgres-backed (so a "no-code UI over Postgres" without a sync): nocodb 65,377 stars, teable 21,935, baserow 6,237 (all pushed 2026-10-29). — GitHub API.

### Inferences
- Because no open-source two-way Airtable↔Postgres sync exists, RoofOps' Airtable-for-staff layer needs its own loop guard; the transferable mechanisms are: a per-record origin/version marker (Airtable's record `id` + a RoofOps `version`/hash column), comparing incoming webhook payloads to the last-written hash before applying, and holding conflicts rather than last-write-wins (ledgerbridge). airtable_pg_sync's id-named tables plus human-named views is a cheap way to survive Airtable field renames.
- NocoDB/Teable/Baserow over the canonical Postgres would eliminate the sync problem entirely, at the cost of Airtable's UX and interfaces; this is a credible fallback if two-way sync proves fragile.

### Gaps
- No engineering write-up explaining echo-loop handling for Airtable specifically was found (Firecrawl searches failed for lack of credits; WebSearch returned only vendor marketing).
- Sequin's earlier Airtable-sync product history is from memory and unverified; the current repo is Postgres CDC only.
