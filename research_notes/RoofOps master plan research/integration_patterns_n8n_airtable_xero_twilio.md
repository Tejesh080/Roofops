## Key question 1: n8n as code — git, deploy, drift, testing

### Takeaway
n8n's native "source control and environments" (git-backed, per-branch environments) is a Business/Enterprise feature and the diff view is Enterprise-only; on Cloud Starter/Pro the realistic "workflows in git" path is the public REST API (available on Starter, Pro, Enterprise, not trial) driven from CI, with workflow JSON as the artifact. n8n explicitly does not detect conflicts (Git is source of truth; pull overrides local), so drift detection has to be built outside n8n (export via API, normalise, diff). Testing is still mostly manual: pinned data is one dataset per node, Evaluations (all Cloud plans) give a dataset-driven "run every row" harness, and there is no native unit-test runner for Code nodes; a formal workflow unit-testing feature request from Jan 2026 is open.

### Cited findings

**Source control and environments (native git)**
- "Available on Business and Enterprise plans." Only instance owners/admins can enable it; project admins can push but not pull. One git branch per environment. — [n8n docs: Source control and environments](https://docs.n8n.io/source-control-environments/)
- What is pushed: workflows, data-table schemas, credential stubs (ID, name, type), tags and variable stubs (ID, name) pushed automatically; projects and folders committed. Credential secrets and variable values are **not** synced; "set them up by hand on each new instance." — [n8n docs: Push and pull](https://docs.n8n.io/source-control-environments/using/push-pull/) and [overview search summary](https://docs.n8n.io/administer/use-source-control-and-environments/push-and-pull-changes)
- Pull overwrites local workflow edits that differ from git (UI button "Pull and override"); resources deleted in git are not auto-removed locally. "n8n can't detect conflicts. Git is the source of truth, so a push overwrites what's in Git." A forced pull "for example, through the API or in automated setups" deletes data tables without a confirmation prompt; the pull endpoint accepts `autoPublish` = `none` | `published` | `all`. — [n8n docs: Push and pull](https://docs.n8n.io/source-control-environments/using/push-pull/)
- Recommended patterns: one-branch (push from dev instance, pull into prod) or multi-branch with the merge done as a PR in the git provider; "Avoid pushing and pulling on the same instance." — [n8n docs: environments tutorial](https://docs.n8n.io/administer/use-source-control-and-environments/tutorial-create-environments-with-source-control)
- Workflow diffs in the commit modal are "Available on Enterprise" and only when environments are enabled. — [n8n docs: Compare changes with workflow diffs](https://docs.n8n.io/source-control-environments/using/compare-changes)
- Pulling from git creates a workflow-history version in the instance DB, not in git. — [n8n docs: Workflow history](https://docs.n8n.io/workflows/history/)

**CLI export/import (self-hosted only)**
- `n8n export:workflow --backup --output=backups/latest/` (backup = `--all --pretty --separate`); `n8n export:workflow --id=<ID> --output=file.json`; `n8n import:workflow --separate --input=backups/latest/`; `--activeState=fromJson` keeps `active` only in multi-main mode; exported IDs are kept on import and matching IDs "will be overwritten". The CLI "runs on the same machine as your n8n installation"; the page gives no Cloud path. — [n8n docs: CLI commands](https://docs.n8n.io/hosting/cli-commands/)

**Public REST API (the Cloud-compatible path)**
- "The n8n API is available on: n8n Cloud Starter, Pro, and Enterprise; self-hosted all editions. It isn't available on the free trial." — [n8n docs: API](https://docs.n8n.io/api/)
- A CI/CD tutorial pattern: one JSON per workflow under `workflows/` exported by CLI; on merge to main, GitHub Actions validates files, waits for a production-environment approval, then "sends a PUT to the n8n public REST API on the prod instance with the workflow body" for each changed workflow, then triggers a test webhook; alternative SSH+CLI route when the API is disabled. — [Lumadock: n8n CI/CD](https://lumadock.com/tutorials/n8n-cicd)
- Community monitor suggestion: poll `GET /api/v1/executions` from outside for status/timing; "Cloud and self-hosted behave the same here." — [n8n community: How are you monitoring n8n workflows in production](https://community.n8n.io/t/how-are-you-monitoring-n8n-workflows-in-production/307194)
- Third-party `n8nctl` (PyPI) advertises a command that "compares local and cloud versions of a workflow JSON file" (unofficial, not verified beyond the listing). — [PyPI: n8nctl](https://pypi.org/project/n8nctl/)
- A 2025 community "GitOps pipeline" companion (Docker client + backend talking to GitHub; push/pull per workflow, diffs between commits, rollback) was a pre-launch beta with no repo link and no drift detection. — [n8n community: Turn your n8n workflows into a real GitOps pipeline (20 May 2025)](https://community.n8n.io/t/turn-your-n8n-workflows-into-a-real-gitops-pipeline/118130)

**Workflow history (in-instance versioning)**
- "Versions from the last 24 hours are available for all users." "Versions from the last five days are available on n8n Cloud Pro." Full history on Cloud Enterprise / self-hosted Enterprise. Named versions on Cloud Pro+ and self-hosted Business+; "n8n never prunes named versions automatically." No built-in diff; compare by opening two versions in tabs; each version can be downloaded as JSON. — [n8n docs: Workflow history](https://docs.n8n.io/workflows/history/)

**Workflows as code (TypeScript)**
- Official package in the n8n monorepo: `@n8n/workflow-sdk`, "TypeScript SDK for programmatically creating n8n workflows", listing "Fluent builder API for workflow creation", "Built-in validation", "Code generation from JSON workflows". Version and npm status could not be read (npm page returned 403). — [GitHub: n8n-io/n8n packages/@n8n/workflow-sdk](https://github.com/n8n-io/n8n/tree/master/packages/%40n8n/workflow-sdk)
- A third-party skill page claims `@n8n/workflow-sdk` v0.2.0 was released February 2026 (**unverified**). — [openskillindex](https://openskillindex.com/skills/terminalskills-skills-n8n-workflow-sdk)
- Community alternatives: `n8n-as-code` (MIT, decorator-based `.workflow.ts`, `n8nac convert` both directions, "not affiliated with n8n") — [n8n-as-code docs](https://etiennelescot.github.io/n8n-as-code/docs/usage/typescript-workflows); `@vahor/n8n-kit` 0.25.0 (TypeScript builder, 400+ node types, deployment tooling) — [README](https://cdn.jsdelivr.net/npm/@vahor/n8n-kit@0.25.0/README.md)

**Workflow collections on GitHub**
- Zie619/n8n-workflows: "4,343 Production-Ready Workflows", "365 Unique Integrations", JSON files under `workflows/` organised by integration, SQLite FTS5 search + FastAPI server, MIT, 57.1k stars. No per-file naming convention or import guidance documented. — [GitHub: Zie619/n8n-workflows](https://github.com/Zie619/n8n-workflows)

**Testing**
- Data pinning freezes a node's output for downstream nodes; "Pinning affects manual executions only; production/triggered executions ignore pins and run all nodes normally." (secondary tutorial; the same statement in official docs was not fetched) — [Rapid Developers: data pinning](https://www.rapidevelopers.com/md/n8n-tutorial/how-to-use-data-pinning-in-n8n)
- Feature request "Workflow Unit Testing with Test Cases" (mnebel, 22 Jan 2026): "At the moment you can pin node output data only once per workflow, thus you can only test one scenario." No n8n staff reply; a community reply says Evaluations "already supports the 'run known cases through the workflow' part very well" but full unit testing is missing; a related proposal "Core FR & Proposal: Workflow Test Harness & Format" was linked 8 Aug 2026. — [n8n community](https://community.n8n.io/t/workflow-unit-testing-with-test-cases/254023)
- Evaluations: run a dataset through a workflow; light (visual) vs metric-based (scored, "rerunning the full dataset as a regression test"). Framed for AI workflows but does not exclude others. — [n8n docs: Evaluations overview](https://docs.n8n.io/advanced-ai/evaluations/overview/)
- Evaluation Trigger outputs "a single item representing one row of your dataset"; "Evaluate all" runs once per row; datasets from data tables or Google Sheets; "Set outputs" writes results back; availability "All plans" on Cloud, "Registered Community, Business, Enterprise" self-hosted. — [n8n docs: Light evaluations](https://docs.n8n.io/advanced-ai/evaluations/light-evaluations/)
- A QA vendor lists "Jest for individual nodes" as a unit-testing option with no detail (**unverified**). — [QAwerk](https://qawerk.com/services/n8n-workflow-testing/)

### Inferences
- For a Cloud Pro-class instance, the practical "n8n as code" loop is: export via `GET /api/v1/workflows/{id}` in CI -> normalise (strip `updatedAt`, `versionId`, pin data, node positions if desired) -> diff against the committed JSON -> fail the job on drift; deploy with `PUT /api/v1/workflows/{id}` then activate. This reconstructs what native source control gives Business/Enterprise, and is the only path that detects drift, because n8n itself states it cannot detect conflicts.
- Because credentials and variable values are never in git in either path, the repo should carry a credential manifest (names/types) and a checklist for re-creating them per instance.
- Testing a Code node's logic is easier if the logic is extracted to a plain TypeScript module tested with a normal test runner, and the Code node kept thin; the official `@n8n/workflow-sdk` makes it plausible to generate and validate the 16 workflow JSONs from TypeScript, but its maturity (v0.x) is unconfirmed.
- Evaluations can serve as a cheap regression harness for non-AI workflows (dataset row in, expected output column compared), which is the closest built-in "test runner" on Cloud.

### Gaps
- Could not read the `@n8n/workflow-sdk` version, publish date or changelog (npm 403; monorepo page does not show package.json).
- No official n8n statement on drift detection beyond "n8n can't detect conflicts"; no first-party tooling found that diffs exported JSON against a live instance.
- No authoritative source found on the webhook-contract-testing practice for n8n (pinned webhook payloads vs real calls); only general tutorials.
- The official data-pinning page (docs.n8n.io/data/data-pinning) was not fetched; the "ignored in production" statement is from a secondary tutorial.

## Key question 2: n8n error handling and alerting in production

### Takeaway
Practitioners converge on three layers: a global Error Trigger workflow (fires only for automatic/production executions, never manual), an external dead-man's switch (Healthchecks.io, Cronitor, UptimeRobot) pinged from scheduled workflows so silence is detected when n8n itself is down or a trigger never fires, and output validation inside workflows because many APIs return 200 with failure in the body. Known gaps: crashed executions produce no Error Trigger, disabled nodes pass data through silently, timed-out/zero-run schedules are invisible, and Cloud execution retention is short (7 days / 2,500 on Starter, 30 days / 25,000 on Pro), with `/metrics` unavailable on Cloud.

### Cited findings

**Error workflows (official behaviour)**
- Set per workflow in Workflow Settings; "must start with the Error Trigger"; one error workflow can serve many workflows; payload has `execution` (id, url, retryOf, error message/stack, lastNodeExecuted, mode) and `workflow` (id, name); `execution.id`/`url` exist only if the execution was saved; trigger-node failures arrive as `WorkflowActivationError` under `trigger{}`. Stop and Error node forces a failure to route to the error workflow. — [n8n docs: Error handling](https://docs.n8n.io/flow-logic/error-handling/)
- "The Error Trigger only runs when an automatic workflow errors." "You can't test error workflows when running workflows manually." "If a workflow uses the Error Trigger node, you don't have to publish the workflow." By default a workflow containing an Error Trigger uses itself as the error workflow. — [n8n docs: Error Trigger node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.errortrigger/)
- Settings: "Save failed production executions", "Save successful production executions", "Save manual executions", "Timeout Workflow" with "Timeout After"; "n8n Cloud enforces a maximum timeout per plan". — [n8n docs: Workflow settings](https://docs.n8n.io/workflows/settings/)

**Execution retention on n8n Cloud**
- Start/Starter: 2,500 executions saved, 7 days; Pro (Pro-1/Pro-2): 25,000, 30 days; Enterprise: 50,000, unlimited. Oldest pruned first when either cap is hit; at DB storage limit only execution data is deleted (records kept); at 85% disk an alert fires and manual pruning may happen (backup then restore without execution data), which "depends on a human response". — [n8n docs: Cloud data management](https://docs.n8n.io/manage-cloud/cloud-data-management/)

**Health endpoints**
- `/healthz`: "200 indicates the instance is reachable. It doesn't indicate DB status." "It's available for both self-hosted and Cloud users." `/healthz/readiness` returns 200 "if the DB is connected and migrated" (Cloud availability not stated). `/metrics` "isn't available on n8n Cloud." — [n8n docs: Monitoring](https://docs.n8n.io/hosting/logging-monitoring/monitoring/)

**What practitioners actually set up (community thread, 2026)**
- Global error workflow -> Slack/Telegram/email with workflow name, error, timestamp (pirateprentice, tariqosmani).
- Output validation after HTTP calls because "Many APIs return `200 OK` with `{"success": false}` buried in the JSON" (pirateprentice).
- Staleness check: write a last-success timestamp to Sheets/Airtable and alert if stale (pirateprentice, ASHIM_DOLEY).
- Log full executions to PostgreSQL and review weekly (tariqosmani); rolling-median run-volume baselines and a "canary" input with exact expected values (themineworks).
- External dead-man's switch: each critical workflow pings Healthchecks.io or Cronitor so alerts still fire if n8n is down; also filter the executions list for "Crashed" status "since those produce no error trigger" (anon45958619); final ping node to Uptime Robot (tariqosmani).
- Gaps reported: a Schedule Trigger missing a field in the JSON that never fired; instance/user timezone mismatch; "zero executions since publish should trigger its own alert"; disabled nodes "pass input through and skip activation validation"; a rolling median "can normalize an outage" (the43sunsets, moneywithjjcom). A Cloud user (KSD) was "exploring an external monitoring layer to avoid editing every workflow". — [n8n community: How are you monitoring n8n workflows in production](https://community.n8n.io/t/how-are-you-monitoring-n8n-workflows-in-production/307194)

**Worked example: 3-workflow supervisor (27 May 2026)**
- Workflow 1 "Supervisor Core": error intake, severity classification, credential sanitisation, deduplication (a single Postgres timeout once "fired 4-5 identical alerts in seconds"), circuit breaker, Telegram alerts with execution link. Workflow 2 "Heartbeat Monitor": every 5 minutes pings Healthchecks.io ("If Healthchecks stops hearing from me something is wrong, guaranteed"), circuit-breaker auto-recovery, error-rate trends, orphan-execution detection via the n8n API. Layers: "Telegram alert -> cache if Telegram fails -> Healthchecks catches silence if everything fails." Self-hosted n8n + Neon Postgres; repo linked as https://github.com/chanrylejay/supervisor-erorr-handling-workflow (spelling in URL differs from link text). — [n8n community: Automated Error Monitoring for n8n (3 workflows, 46 nodes, zero AI)](https://community.n8n.io/t/automated-error-monitoring-for-n8n-3-workflows-46-nodes-zero-ai/297209)
- A vendor post describes an outage where "the workflows had not crashed. They had just stopped being triggered", the case for heartbeat checks. — [Web Project Studios: n8n workflow observability in production (June 2026)](https://webprojectstudios.co.uk/blog/2026-06-n8n-workflow-observability-production)

### Inferences
- On n8n Cloud the only first-party signals are the Error Trigger, the executions API/list, `/healthz`, and the executions UI; everything about "silence", "crashed", "timed out" and "never scheduled" has to be externalised (heartbeat pings to Healthchecks.io-style services plus a periodic executions-API poll for status `crashed`/`error` counts).
- Retention of 7 days on Starter / 30 days on Pro means incident evidence disappears quickly; the community practice of logging a compact execution record to your own Postgres (the system already has Supabase) is the cheap fix.
- Alert deduplication/suppression is a recurring need (storms from one outage); a `processed_alerts`/dedupe key keyed by workflow+error class within a window matches what the supervisor example built.

### Gaps
- No official n8n statement found on whether the Error Trigger fires for executions that time out ("Timeout Workflow") or are cancelled; community reports only cover "Crashed".
- Whether `/healthz/readiness` is reachable on Cloud is not stated in the docs.
- No primary data on how often Cloud alerts/pruning actually lag; the "85% disk" manual process is documented but no incident data was found.

## Key question 3: Airtable <-> Postgres two-way sync

### Takeaway
There is no first-party Airtable<->Postgres two-way sync: Airtable's native two-way sync is base-to-base only (Business/Enterprise Scale) and its external sync integrations (e.g. Snowflake) are one-way and Enterprise Scale; Airbyte/Fivetran are extract-only sources; Sequin, the best-documented Airtable->Postgres replicator (2021), has since become a Postgres CDC product with no Airtable support; Whalesync is the main commercial two-way option and resolves conflicts by "most recent changes win". Practitioners consistently report echo loops, phantom/duplicate records and rollbacks to one-way sync, and the standard advice is one system of record per field with a sync log for conflicts. Airtable's hard limits (5 req/s per base, 10 webhooks per base, 7-day webhook expiry, ping-only notifications) shape any home-grown sync.

### Cited findings

**Airtable platform limits that constrain sync**
- "5 requests per second per base"; "50 requests per second" for all traffic using personal access tokens from a user/service account; exceeding returns 429 and "you will need to wait 30 seconds before subsequent requests will succeed"; the official JS client retries automatically; Airtable "may change the enforced API rate limits ... in our sole discretion". — [Airtable developers: Rate limits](https://airtable.com/developers/web/api/rate-limits)
- Monthly API call caps apply to Free and Team plans; once the Team cap is reached calls are "throttled to 2 requests per second"; a 429 at low rates can mean the monthly cap was hit. — [Airtable support: Managing API call limits](https://support.airtable.com/managing-api-call-limits-in-airtable)
- Webhooks: "webhooks created with personal access tokens or OAuth access tokens will expire and be disabled after 7 days"; refresh (or listing payloads) extends 7 days from refresh time; the notification is a ping (base ID + webhook ID) and changes are fetched separately via list webhook payloads; body hash in `X-Airtable-Content-MAC` as `hmac-sha256=<hex>` using the hook's MAC secret; User-API-key webhooks are Enterprise-only and "can no longer be created". — [Airtable developers: Webhooks overview](https://airtable.com/developers/web/api/webhooks-overview)
- "The number of webhooks per base is limited to 10"; a single OAuth integration can create up to 2 per base; after expiry, metadata and past payloads remain for a further 7 days; `expirationTime` is null for User API keys. — [Airtable developers: Create a webhook](https://airtable.com/developers/web/api/create-a-webhook)

**Airtable's own sync features**
- Two-way sync is Airtable base <-> Airtable base only ("Add from other sources" -> "Airtable base"); "Business and Enterprise Scale plans only"; record creation/deletion in targets "turned off by default"; attachment fields read-only in targets; button/formula/computed fields not syncable; no daisy-chaining; "Edits cannot be made using API calls in target bases"; undo may not reach the source so "the next sync can restore edited values"; source views over 200,000 cells cannot be used. No conflict-resolution policy is described. — [Airtable support: Two-way syncing in Airtable](https://support.airtable.com/docs/two-way-syncing-in-airtable)
- Snowflake sync integration is one-way into Airtable, Enterprise Scale, scheduled 1/3/6/12/24 h. No native PostgreSQL sync source was found. — [Airtable support: Airtable Sync integration: Snowflake](https://support.airtable.com/articles/3035678367-airtable-sync-integration-snowflake)

**Third-party tools**
- Whalesync markets "TWO WAY, REAL-TIME SYNC" Postgres<->Airtable, but some of its connector pages simultaneously say "Postgres isn't avaiable to sync yet" and "Status: Live" (stale/conflicting copy). — [Whalesync: Postgres-Airtable](https://www.whalesync.com/sync/postgres-airtable); [Whalesync: Postgres connector](https://www.whalesync.com/connector/postgres)
- Whalesync docs: when both sides change a paused record, "the most recent changes win" (its only documented last-write rule). — [Whalesync docs: Selective sync](https://docs.whalesync.com/features/additional-features/selective-sync)
- Whalesync docs: Airtable synced tables cannot be overwritten ("Airtable does not allow you to overwrite this data on synced tables"), so make the sync one-way or convert the table. — [Whalesync docs: Common errors Airtable](https://docs.whalesync.com/resources/support/common-errors-airtable)
- Stacksync (competitor) claims field-level conflict resolution and loop prevention "by design"; vendor claim, not independently verified. — [Stacksync: conflict resolution engine](https://stacksync.com/blog/deep-dive-stacksyncs-conflict-resolution-engine-for-bidirectional-crm-integration)
- Sequin today: "the fastest change data capture (CDC) platform for Postgres", a Docker container streaming to Kafka/SQS/Pub/Sub/Elasticsearch/Redis/webhooks; MIT; README does not mention Airtable. — [GitHub: sequinstream/sequin](https://github.com/sequinstream/sequin)
- Sequin's 2021 engineering post (Anthony Accomazzo, **2 July 2021**) on Airtable->Postgres replication cites Airtable's "difficulty in detecting changes", "a flexible schema" and "low throughput"; they moved from "rebuild sync" (reconstruct DB each sync) to upserts into the public schema to reduce lag/writes, then in-memory fingerprinting to cut reads. — [Sequin blog mirror](https://www.plushcap.com/content/sequin/blog/sequin-our-airtable-sync-process-layer-by-layer); [dev.to cross-post](https://dev.to/acco/our-airtable-sync-process-layer-by-layer-58l9)
- `airtable-pg-sync` (PyPI): one-way "replicating an entire Airtable base in a Postgres schema", one-off or perpetual mode. — [PyPI: airtable-pg-sync](https://pypi.org/project/airtable-pg-sync/)
- Airbyte's Airtable connector is a *source* (OAuth/API key, Full Refresh or Incremental, into 50+ destinations); the Airbyte agent connector for Airtable "cannot create, update, or delete records". — [Airbyte: Airtable connector](https://airbyte.com/connectors/airtable)
- Fivetran's Airtable connector launch post (**April 2021**) describes pulling data from Airtable (extract direction). — [Fivetran blog](https://fivetran.com/blog/new-connector-airtable)

**Practitioner reports on two-way sync**
- Latenode forum: simultaneous edits on both sides "leads to conflicts or duplicate records"; a client's bidirectional sync "worked great for two months then started creating phantom records", and the user "rolled back to one-way push". — [Latenode community](https://community.latenode.com/t/looking-for-working-bidirectional-sync-solution-between-notion-and-airtable-whats-your-experience/24075)
- n8n two-way Airtable<->Sheets guide: two-way "has higher risk" and needs explicit rules for same-field/same-window changes; recommends logging conflicts to a separate "Sync Log" for review. — [DEV: n8n Airtable to Google Sheets two-way sync](https://dev.to/pirateprentice/n8n-airtable-to-google-sheets-two-way-sync-that-actually-doesnt-break-1aac)
- Loop-avoidance guide (2026): loops occur when both systems can edit the same field and each update re-triggers the other; give each field one owner. — [pravinkumar.co: Airtable + HubSpot without loops](https://www.pravinkumar.co/blog/how-to-keep-airtable-and-hubspot-in-sync-without-loops-2026)
- Vendor framing: Airtable native sync "is read-only, limited to Airtable bases, refreshes periodically and has no conflict resolution" (Stacksync, biased). — [Stacksync: Airtable sync](https://www.stacksync.com/blog/airtable-sync-two-proven-ways-sync-data.md)

### Inferences
- The existing RoofOps design (Postgres canonical + Airtable editing surface via outbox + webhooks) is already the shape the literature recommends; the remaining risk is per-field ownership: any field editable in both places needs an explicit owner or a last-writer rule plus a sync log, and echo suppression (ignore Airtable webhook payloads whose change originated from your own API writes, e.g. by comparing to the last value you wrote or tagging writes).
- Airtable's ping-only webhooks with 7-day expiry mean two maintenance jobs are mandatory in any home-grown sync: a refresh job (<7 days) and a cursor-based payload fetch with retry; a nightly full reconciliation (compare `lastModifiedTime` per record) is the standard guard against missed pings.
- At 5 req/s per base, bulk writes (e.g. re-syncing hundreds of records) must be batched (10 records per request) and queued; this is where a home-grown sync most often silently drops edits (429 + no retry).
- Moving to Airtable-reads-only (Interfaces/forms as the edit surface writing straight to Postgres via webhook, Airtable as a mirror) is the "one editing surface" path the forum rollbacks describe; this is a judgement, not a cited case study.

### Gaps
- No published case study of a team specifically moving off Airtable<->Postgres two-way sync; only forum anecdotes (Notion/Airtable, HubSpot/Airtable).
- Whalesync's loop-prevention mechanism and Postgres connector availability could not be confirmed from its docs (conflicting page copy).
- No source confirming whether Sequin formally announced sunsetting its Airtable product; only the absence of Airtable in the current README.
- Airtable webhook notification rate limits/retry behaviour for the ping are not documented on the pages fetched.

## Key question 4: Xero API from Node/TypeScript

### Takeaway
xero-node (latest release 18.1.0) is the official SDK; its generated API methods carry an optional `idempotencyKey` argument that is sent as the `Idempotency-Key` header (confirmed in SDK source for `createContacts`; the OpenAPI spec references the same parameter on many operations; Xero added it to all PUT/POST/PATCH in Dec 2023). Rate limits are 60/min, 5,000/day, 5 concurrent per tenant and 10,000/min per app, with 429 and `X-*Limit-Remaining` headers. Webhooks are signed with base64 HMAC-SHA256 of the raw body using the webhook key in `x-xero-signature`, validated by an "Intent to Receive" that expects 401 on a bad signature; the SDKs ship no helper. The demo company resets after 28 days (third-party sources). Invoice status enum is DRAFT/SUBMITTED/DELETED/AUTHORISED/PAID/VOIDED; AU GST codes OUTPUT (GST on Income), INPUT (GST on Expenses), EXEMPTOUTPUT (GST Free Income), BASEXCLUDED are confirmed from SDK enums and a third-party table, not from Xero's JS-rendered docs.

### Cited findings

**SDK**
- xero-node README: access token is a "Bearer token with a 30 minute expiration required for all API calls"; refresh token 60-day expiry; `await xero.refreshToken()` or `xero.refreshWithRefreshToken(clientId, clientSecret, refreshToken)`; invoice example uses `xero.accountingApi.createInvoices(activeTenantId, invoices)` with `taxType`, `accountCode`, `status: Invoice.StatusEnum.AUTHORISED`. README does not mention rate limits or idempotency. — [GitHub: XeroAPI/xero-node](https://github.com/XeroAPI/xero-node)
- Latest release 18.1.0 (21 Sep; year not shown), note "redact request headers from error objects". — [GitHub: xero-node releases](https://github.com/XeroAPI/xero-node/releases)

## Key question 5: Twilio SMS in Australia (lead follow-up, trial-to-production, webhooks, opt-out)

### Takeaway
In Australia Twilio supports alphanumeric sender IDs only with pre-registration (since 25 April 2023) and, from 1 July 2026, only if registered on ACMA's Sender ID Register; unregistered IDs are delivered as "Unverified". Alphanumeric IDs are one-way (no STOP replies, so you must provide another opt-out), unavailable on trial accounts, and processed one at a time with ASIC extract, brand proof and government ID. For two-way lead follow-up an AU mobile (long code) number is the sender that supports replies and STOP; business mobile numbers need business name, business ID (ABN/ACN) and address proof. Trial accounts can only message up to 5 verified recipients (21608/14111), only from the assigned trial number (21607/572002), 50 messages/day, with a "Sent from a Twilio Trial account" prefix and templated bodies; trials expire after 30 days. Inbound webhooks are validated by HMAC-SHA1 over the exact URL + sorted POST params with the auth token (`X-Twilio-Signature`), using `validateRequest`; JSON bodies use `bodySHA256`. Direct n8n+Airtable+Twilio lead-follow-up templates exist but are thin.

### Cited findings

## Key question 6: Transactional outbox and idempotent webhook processing in Postgres (and when it is over-engineering)

### Takeaway
The canonical definitions (microservices.io) are: write the message to an outbox table in the same transaction as the business change, have a relay (polling publisher or log tailing) deliver it, accept at-least-once delivery, and make consumers idempotent by recording processed message IDs in the same transaction (a `processed_events`/inbox table with a unique key). Supabase's primitives map onto this: database webhooks are pg_net triggers (async, fire after commit, 2 s default timeout, responses kept 6 h, no retries or signing documented), and Supabase Queues (pgmq, launched 5 Dec 2024) gives guaranteed delivery with exactly-once-within-visibility-window semantics. Practitioner guidance is that a single polling worker with `FOR UPDATE SKIP LOCKED` is enough well past small-business volumes, and that the pattern is overkill when losing an event is harmless but justified when a lost event costs money (invoices, customer messages).

### Cited findings

**Canonical pattern**
- Problem: "How to atomically update the database and send messages to a message broker?" without 2PC. Solution: "store the message in the database as part of the transaction that updates the business entities. A separate process then sends the messages to the message broker." Message outbox = "a table that stores the messages to be sent"; relay via transaction log tailing or polling publisher. "Messages are guaranteed to be sent if and only if the database transaction commits." Drawback: developer "might forget to publish the message"; the relay "might publish a message more than once" so consumers should be idempotent. Event sourcing is an alternative. — [microservices.io: Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)
- Polling publisher: "Publish messages by polling the database's outbox table"; benefit "Works with any SQL database"; drawbacks "Tricky to publish events in order", "Not all NoSQL databases support this pattern". — [microservices.io: Polling publisher](https://microservices.io/patterns/data/polling-publisher.html)
- Idempotent consumer: "Make a consumer idempotent by having it record the IDs of processed messages in the database"; with a separate table keyed `(subscriberId, messageID)` the handler inserts the ID first in its transaction and "INSERT will fail if the message has been already processed successfully", then rolls back and ignores; "the outcome of processing the same message repeatedly must be the same as processing the message once". — [microservices.io: Idempotent consumer](https://microservices.io/patterns/communication-style/idempotent-consumer.html)
- Stripe's webhook guidance (industry reference for the receiver side): "guard against duplicated event receipts by logging the event IDs you've processed, and then not processing already-logged events"; "Stripe doesn't guarantee the delivery of events in the order that they're generated"; "Don't use `created` to determine event order or whether you've already processed an event. Track event IDs"; return 2xx "before any complex logic"; process "with an asynchronous queue"; retries "for up to three days with an exponential backoff"; raw body required for signature verification; replay protection via timestamp with 5-minute default tolerance. — [Stripe docs: Webhooks](https://docs.stripe.com/webhooks)
- Postgres relay specifics: `FOR UPDATE SKIP LOCKED` so multiple publishers don't claim the same rows; outbox row ID as message ID; at-least-once ("if the relay crashes after publishing but before marking a row sent, the event is republished"); consumer dedupe via `INSERT ... ON CONFLICT DO NOTHING` projection or an inbox table; outbox tables grow unboundedly so delete/archive dispatched rows or partition. — [Conduktor: Transactional outbox](https://conduktor.io/blog/transactional-outbox-pattern-database-kafka); [DEV: Outbox pattern in Postgres end to end](https://dev.to/gabrielanhaia/outbox-pattern-in-postgres-end-to-end-producer-relayer-consumer-2k75)

**Supabase primitives**
- Database Webhooks are "a convenience wrapper around triggers using the pg_net extension"; "asynchronous, and therefore will not block your database changes for long-running network requests"; events INSERT/UPDATE/DELETE "fired after a database row is changed"; payload `type, table, schema, record, old_record`; history "available under the `net` schema"; the page does not mention retries, delivery guarantees or failure handling; a secret key stored in a trigger is visible to any role that can log in and is written decrypted to `net.http_request_queue` until sent. — [Supabase docs: Database webhooks](https://supabase.com/docs/guides/database/webhooks)
- pg_net: `timeout_milliseconds` defaults to 2000; "The response messages are stored for only 6 hours"; configured to "reliably execute up to 200 requests per second" ("Increasing the rate can introduce instability"); "HTTP requests are not started until the transaction is committed"; queue uses unlogged tables so data is "not preserved during a crash or unclean shutdown"; dropping the extension deletes pending requests; no retry/delivery guarantee is documented. — [Supabase docs: pg_net](https://supabase.com/docs/guides/database/extensions/pg_net)
- Secondary summary of the same: "There is no delivery id header and no documented retry policy"; "Supabase does not sign it. The only authentication is whatever headers you put in the trigger definition"; "Idempotency is your receiver's job: dedupe on a primary key inside `record` / `old_record`." — [Hookdeck: Guide to Supabase webhooks](https://hookdeck.com/webhooks/platforms/guide-to-supabase-webhooks-features-and-best-practices.md)
- Supabase Queues "built on the pgmq database extension"; "Messages added to Queues are guaranteed to be delivered to your consumers"; "A Message is delivered exactly once to a consumer within a customizable visibility window." — [Supabase docs: Queues](https://supabase.com/docs/guides/queues); announced 5 Dec 2024 (pgmq from Tembo, PostgreSQL licence). — [Supabase blog: Supabase Queues](https://supabase.com/blog/supabase-queues); pull-based consumption from Edge Functions (read batch, process, delete; failed messages reappear after the visibility window; schedule via cron or on demand). — [Supabase docs: Consuming messages with Edge Functions](https://supabase.com/docs/guides/queues/consuming-messages-with-edge-functions)
- Community example: webhook handler calls `pgmq_send`, a cron-triggered processor calls `pgmq_read` (pgmq + pg_cron + Edge Functions). — [DEV: Build queue worker using Supabase cron, queue and edge function](https://dev.to/suciptoid/build-queue-worker-using-supabase-cron-queue-and-edge-function-19di)

**When it is over-engineering**
- "One worker beats one cluster when the team is five engineers and one of them is the on-call." "A single polling worker on a t3.medium handles 10k events/sec with room." Poll when "You're under ~5k events/sec", no Kafka, single region, schema still changing; "Most business events fall in the second bucket" (invoicing, email triggers, analytics checked within minutes). CDC/Debezium only when you "already operate Kafka Connect", need sub-second latency, or exceed ~20k events/sec. Worker: select `outbox_events WHERE published_at IS NULL ORDER BY id LIMIT 500 FOR UPDATE SKIP LOCKED`, publish, flush, then mark published in the same transaction. — [DEV: Outbox pattern - when CDC beats polling, when polling beats CDC](https://dev.to/gabrielanhaia/outbox-pattern-when-cdc-beats-polling-when-polling-beats-cdc-4dj4)
- The inbox and outbox patterns "can be overengineering since there are simpler alternatives". — [Codely: Inbox and Outbox course](https://codely.com/en/courses/design-patterns-inbox-and-outbox-1n0u)
- Rule of thumb from a deep-dive: if events are "a statement of fact that something occurred within your system, it's probably not overengineering"; if they are best-effort analytics where missing some is fine, the pattern is unnecessary; the pattern adds "a table, a hosted service, and a dispatch loop", and naive frequent `SELECT`s on unprocessed rows become "a massive contention point once several instances run". — [Ritualworks: Transactional outbox deep dive](https://ritualworks.pages.dev/deep-dives/transactional-outbox)
- The pattern "is equally powerful in monoliths for reliable external integration", citing webhook delivery. — [DEV: The outbox pattern, a love letter to eventual consistency](https://dev.to/igornosatov_15/the-outbox-pattern-a-love-letter-to-eventual-consistency-3ch3)

### Inferences
- For RoofOps the outbox is justified on the edges where loss or duplication costs money or trust: Postgres -> Xero draft invoices and Postgres -> Twilio/Airtable notifications. It is overkill for best-effort mirrors (e.g. dashboards) and for anything that can be rebuilt by a nightly reconciliation.
- The simplest sound stack on Supabase is: outbox table written in the business transaction; a single relay (pg_cron-scheduled Edge Function or n8n schedule) draining with `SKIP LOCKED` and marking rows sent; receivers keyed by a `processed_events (source, event_id)` unique index inserted in the same transaction as the side effect. Database Webhooks via pg_net are fine as a *trigger* for "go drain the outbox now" but not as the delivery mechanism, because pg_net has no retries, a 2 s timeout and no signing.
- Supabase Queues can replace a hand-rolled relay if the enqueue happens inside the same transaction as the business write (pgmq is in the same database, so `SELECT pgmq.send(...)` in the transaction preserves atomicity); this trades a custom outbox table for pgmq's visibility-timeout semantics and a dead-letter approach.
- Webhook receivers for Airtable (ping), Xero (thin events) and Twilio (status callbacks) all benefit from the same two-step shape Stripe documents: verify signature on the raw body, insert `(source, event_id)` or return 2xx immediately, enqueue, process asynchronously, and tolerate out-of-order delivery by fetching current state rather than trusting payload order.

### Gaps
- No Supabase-authored guide specifically on implementing a transactional outbox with pg_net or pgmq was found; the mapping above is an inference from the primitives' documented behaviour.
- No quantitative guidance for sub-100-events/day systems (all throughput numbers found are thousands per second); the "when not to bother" advice is qualitative.
- Supabase Queues' current GA/alpha status is inconsistent across pages (features page "Public Alpha" vs docs "production-ready"); not resolved.
