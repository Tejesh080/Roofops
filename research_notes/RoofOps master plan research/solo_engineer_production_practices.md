# Solo-engineer production practices: prototype (Supabase + Next.js/Vercel + n8n) to trusted system

Research date: 29 October 2026. Sources are current as of that date unless an older date is given. Workflow YAML was fetched directly from the named repositories' default branches on this date; everything else was fetched or searched on this date. "Search snippet" means the claim comes from a search-engine summary of a page I did not open; treat those as weaker.

Context assumed throughout: ~1,300 vitest tests (PGlite + Postgres 17 in Docker), 64 SQL migrations with hand-written rollback files, Playwright specs, no CI, no staging, no alerting, one hosted Supabase project, Next.js dashboard on Vercel, 16 n8n Cloud workflows exported as JSON.

## 1. CI for Postgres-heavy TypeScript projects on GitHub Actions

### Takeaway
The canonical pattern in every well-known repo examined is identical: a `services: postgres:` block with `pg_isready` health checks and port `5432:5432`, `localhost` as the host, migrations applied from scratch on every PR, Playwright with `--with-deps` and sharding, `concurrency: cancel-in-progress`, and a package-manager cache via `actions/setup-node`. Several repos additionally run a "migrations match schema" check (`prisma migrate diff --exit-code`, `supabase db diff --strict-coverage`), and Cal.com caches a seeded `pg_dump` between jobs. Measured e2e runtimes in Formbricks: 7.6–8.7 min per job on an 8-vCPU runner vs 17.8+ min on GitHub's free 4-vCPU runner.

### Cited Findings

**Official pattern**
- GitHub's reference PostgreSQL service container: `image: postgres`, `env: POSTGRES_PASSWORD: postgres`, `options: --health-cmd pg_isready --health-interval 10s --health-timeout 5s --health-retries 5`, `ports: - 5432:5432`. When the job runs directly on the runner, "The hostname is `localhost` or `127.0.0.1`"; when the job itself runs in a container, the hostname is the service label (`postgres`) and `ports` can be omitted. — [GitHub Docs](https://docs.github.com/en/actions/use-cases-and-examples/using-containerized-services/creating-postgresql-service-containers)
- Playwright's recommended GitHub workflow: `actions/checkout@v6`, `actions/setup-node@v6` (`node-version: lts/*`), `npm ci`, `npx playwright install --with-deps`, `npx playwright test`, then `actions/upload-artifact@v5` with `if: ${{ !cancelled() }}` and `retention-days: 30`. "Caching browser binaries is not recommended" because restoring takes about as long as downloading, and Linux OS deps "are not cacheable". Sharding is done with a matrix. The "On deployment" pattern sets `PLAYWRIGHT_TEST_BASE_URL` to the deployed URL: "Services like Vercel use this pattern so you can run your end-to-end tests on their deployed environment." — [Playwright CI docs](https://playwright.dev/docs/ci)
- GitHub Actions billing: GitHub Free (personal) includes $12 USD of compute per month (≈2,000 Linux 2-core minutes at $0.006/min; my calculation), Pro $18; 500 MB artifact storage on Free; 10 GB cache per repository; standard GitHub-hosted runners are free in public repositories. — [GitHub Docs](https://docs.github.com/en/billing/managing-billing-for-your-products/about-billing-for-github-actions)

Demo repo: github.com/supabase/supabase-action-example. — [Supabase: Managing environments](https://supabase.com/docs/guides/deployment/managing-environments)

### Inferences
- A minimal RoofOps CI is three jobs in one workflow: (1) `unit` — vitest against PGlite, no service, ~15-min timeout; (2) `db` — `postgres:17` service, apply all 64 migrations from an empty DB, run the Postgres-backed vitest suite, then `pg_dump --schema-only` and diff against a committed `schema.sql` (the Supabase/Cal.com "migrations match schema" check, done with plain `pg_dump` since the project uses raw SQL); (3) `e2e` — Playwright, 1–2 shards, `--with-deps`, artifact upload with `if: ${{ !cancelled() }}`. Add `concurrency: cancel-in-progress` and `paths:` filters from day one.
- Expected runtime for this size on free 2-core runners: unit+db in the 3–8 min range, e2e 10–20 min (Formbricks' 17.8+ min is a much larger suite). Shard e2e only once it exceeds ~10 min. Private-repo budget: ~2,000 min/month on GitHub Free is roughly 60–100 PR runs; a public repo is unlimited.
- "Run migrations against a dump/restore" is cheap to add as a scheduled (weekly) job: `supabase db dump` a sanitised schema+data file into an artifact (or S3), restore it into the `postgres:17` service, apply any migrations newer than the dump's version, run the suite. Cal.com's `cache-db` action is a drop-in template for the dump/restore mechanics.
- Keep Playwright browsers uncached (Playwright's own advice); cache only `node_modules` via `setup-node`.

### Gaps
- No primary source gives a benchmark for a ~1,300-test vitest suite; the user must measure. Formbricks' numbers are the only measured runtimes found in a real workflow.
- I did not fetch Drizzle's or Prisma's example-repo workflows; Drizzle's repo workflows are release-oriented (`release-feature-branch.yaml`, etc.) rather than a canonical Postgres test workflow.

## 2. Staging for Supabase (branches vs second project; Vercel previews)

### Takeaway
Supabase Branching is Pro-plan-and-above ($25/mo) and costs $0.01344 per branch-hour (≈$0.32/day on Micro); branches start empty by default and must be seeded; the Vercel integration injects branch credentials into preview deployments at PR-open time. Supabase's own "Managing environments" guide recommends a separate staging project driven by `supabase db push` from a `develop` branch. For a solo engineer the cheapest credible setup is: production on Pro (needed for daily backups anyway), staging as a second project (Free tier, accepting the 1-week auto-pause, or a persistent branch at ~$10/month), and a Vercel Hobby `staging` preview branch with branch-scoped env vars.

### Cited Findings
- Preview branches "are ephemeral and best suited for focused testing" and are deleted automatically when their PR is merged or closed; persistent branches are "long-lived and recommended for environments like staging, QA, or development" and aren't paused or deleted for inactivity. Each branch is "a separate environment with its own Supabase instance and API credentials." The schema is not cloned; a GitHub-connected branch builds it from repository migrations. "By default, new branches do not start with any data or storage objects from your base project. This is meant to better protect your sensitive production data." Data can be added via a seed file (GitHub integration) or the dashboard "Include data" option. Auth secrets (OAuth, SMTP) get placeholder values and must be set per branch. Merging triggers deployment steps Clone, Pull, Health, Configure (GitHub only), Migrate, Seed, Deploy; the Health step waits up to 2 minutes. Dashboard branching is "currently in beta." — [Supabase Branching](https://supabase.com/docs/guides/deployment/branching)
- Pricing: Branching is "available on the Pro Plan and above", listed as "Not included" on Free; "$0.01344 per branch, per hour". Pro "From $25 per month" with "$10 per month" compute credits. Free: two active projects, "Free projects are paused after 1 week of inactivity", automatic backups "Not included". Daily backups: Pro 7 days, Team 14 days. PITR: $100/month per 7 days of retention. Log drains: $60/drain/month + $0.20 per million events + $0.09/GB egress. — [Supabase Pricing](https://supabase.com/pricing)
- Branch billing detail: default compute is Micro, "starts at $0.01344 per hour"; FAQ: "No, Compute Credits do not apply to Branching Compute" (the page's own worked example nonetheless subtracts a $10 credit from a subtotal that includes branch lines — internally inconsistent); example shows a preview branch running 30 hours billed $0.40 compute + $1 egress; persistent branches "will remain active even after the underlying PR is closed." — [Supabase: Manage Branching usage](https://supabase.com/docs/guides/platform/manage-your-usage/branching)
- Vercel integration: "Supabase automatically updates your Vercel project with the correct environment variables" for the matching preview branch; sync happens when a pull request is opened, not at branch creation; "there are possible race conditions between Supabase setting correct variables, and Vercel running a deployment process", so Supabase "is always automatically re-deploying the most recent deployment of the given pull request." Requires the Vercel GitHub integration and connecting the Supabase project to the Vercel project. — [Supabase Branching integrations](https://supabase.com/docs/guides/deployment/branching/integrations)
- Vercel environments: a preview deployment is created on every push to a non-production branch or PR. Staging options table: "Custom staging environment" (Pro and Enterprise; 1 included per project, extra packs of five at $50/month), "Preview branch for staging" ("All plans, including Hobby": create a `staging` branch, assign `staging.example.com` to it, add branch-specific Preview env vars which "override Preview variables with the same name"), and "Staged production deployment" (all plans: disable auto-assign of production domains, verify via generated URL, then promote without rebuilding; "Staged production deployments use production environment variables, so testing can access production services and data"). — [Vercel: Environments](https://vercel.com/docs/deployments/environments)
- Supabase's recommended three-environment model: Local (`supabase start`, one per feature branch or git worktree) → Staging (`develop` branch, "Dedicated staging Supabase project", "Verify migrations before release") → Production (`main`). Staging must be a fresh project: "A project which has already been modified to reflect the production project's schema can't be used because the CLI would reapply these changes." For dashboard-made changes, run `supabase db pull` first to capture them as a migration; verify alignment with `supabase migration list`; if migrations collide, rename to a newer timestamp and `supabase db reset`. The guide does not cover seed data. — [Supabase: Managing environments](https://supabase.com/docs/guides/deployment/managing-environments)
- `supabase db dump` excludes Supabase-managed schemas ("include auth, storage, and those created by extensions"); `--data-only`, `--role-only`, `--schema`, `--linked` (requires `supabase link`) vs `--local`, `-f` output file. — [Supabase CLI: db dump](https://supabase.com/docs/reference/cli/supabase-db-dump)
- Practitioner failure mode of a Free-tier staging/prod project: "Free-tier projects auto-pause after 7 days of inactivity" and the app went blank for a day with nobody notified (search snippet). — [dev.to/astraedus](https://dev.to/astraedus/5-monitoring-blind-spots-that-let-my-side-projects-fail-silently-km3)
- Vercel Marketplace Supabase listing warns to "exercise extreme caution with any environment variables from Supabase, especially any environment variables containing secret values" and lists the injected vars (`SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_JWT_SECRET`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `POSTGRES_URL`, …) (search snippet). — [docs.vercel.com/marketplace/supabase](https://docs.vercel.com/marketplace/supabase)

### Inferences
- Cost ladder for a solo engineer (Oct 2026 list prices): (a) staging = second Free project: $0, but auto-pauses after 7 idle days and has no backups — fine for staging if you accept un-pausing before a release; (b) staging = persistent Supabase branch on a Pro production project: ≈$10/month on top of $25 Pro; (c) per-PR preview branches: ≈$0.32/day each while open, so close PRs promptly. Vercel Hobby covers the app side for free via the `staging` preview-branch pattern; Vercel custom environments are Pro-only.
- Because branches start with no data, seeding is the real work: commit a `supabase/seed.sql` of synthetic roofing jobs/customers (never a production dump) so that both branches and the local `supabase start` DB are identical to what CI tests against.
- The "staged production deployment" option on Vercel (verify the exact production build on its generated URL, then promote) is a free, zero-infrastructure smoke-test step, but it uses production env vars and therefore the production DB — treat it as read-only verification only.

### Gaps
- Supabase documents no data-anonymisation tooling for branches; the only sanctioned path is seed files or opt-in "Include data." Anonymised-copy workflows would need a hand-written `pg_dump --data-only` + scrubbing script (no Supabase guidance found).
- Whether branch Micro compute is covered by Pro compute credits is contradictory within Supabase's own docs (see above); budget as if it is not.

## 3. Migration safety (expand/contract, rollback files vs forward-only, backup rehearsals)

### Takeaway
Practitioners with the most experience (Atlas's maintainer, Stripe, Fowler/Thoughtworks) converge: hand-written down files are rarely executed in production, cannot restore dropped data, and are written against an assumed-successful state; the safety net that actually works is expand/contract (schema stays a superset so the previous app build keeps working), a backup taken before any destructive step, transactional migrations, and CI that applies the full migration chain from scratch. Keep the 64 rollback files as documentation and test one or two in CI, but do not treat them as the recovery plan.

### Cited Findings
- Parallel Change (expand → migrate → contract), 13 May 2014, Danilo Sato: "a pattern to implement backward-incompatible changes to an interface in a safe manner"; "Most database refactorings follow the parallel change pattern"; skipping the contract phase leaves the codebase worse, so mark deprecations with TODOs. — [martinfowler.com/bliki/ParallelChange](https://martinfowler.com/bliki/ParallelChange.html)
- Stripe "Online migrations at scale", 2 Feb 2017, Jacqueline Xu: four phases — dual writing (with backfill), change read paths, change write paths, remove old data; "We never attempted to change more than a few hundred lines of code at one time"; Scientist experiments "alerted us as soon as a single piece of data was inconsistent in production." — [stripe.com/blog/online-migrations](https://stripe.com/blog/online-migrations)
- "The Myth of Down Migrations", 1 Apr 2024, Ariel Mashraki (Atlas): "down migration files are actually a bad idea and should be actively avoided"; "In my entire career, working on projects with thousands of down files, I never applied them on a real environment"; down files are written before the up runs and assume it succeeded, so after a partial failure "they cannot guarantee correctness when applied to the database at runtime"; reverting an added column with `DROP COLUMN` "deletes all the data in that column"; across customer interviews only one team routinely ran down files in production. Atlas instead computes a revert plan from the live DB state with pre-checks that the plan won't delete data, `--dry-run`, and transactional execution where supported. — [atlasgo.io blog](https://atlasgo.io/blog/2024/04/01/migrate-down); HN threads [39898350](https://news.ycombinator.com/item?id=39898350), [42720379](https://news.ycombinator.com/item?id=42720379)
- "Why I don't use down migrations" (Freek Van der Herten, Aug 2025; HN item 45038253, 3 points) — not fetched; title and URL only. — [freek.dev](https://freek.dev/2900-why-i-dont-use-down-migrations)
- Prisma: Prisma Migrate has no native down; you generate one yourself with `prisma migrate diff ... --to-migrations prisma/migrations` ("the preferred option, as it is more robust") into `down.sql`; applying it is `db execute --file ./down.sql` then `migrate resolve --rolled-back <name>`, and that step "can only be used on failed migrations"; "other changes to data and application code that are carried out as part of the up migration will not be reverted"; custom SQL (views, triggers) must be reversed by hand. — [Prisma docs](https://www.prisma.io/docs/orm/prisma-migrate/workflows/generating-down-migrations)
- Secondary practitioner posts (search snippets, not opened): "Forward-only. Down-migrations lie; they're rarely tested and often impossible (you can't un-drop data). Rolling back means deploying a new forward migration." — [pandastack.io](https://pandastack.io/blog/zero-downtime-database-migrations); "Expand/contract makes app rollback always safe because the schema is always a superset of both versions' needs" — [gocdnext docs](https://klinux.github.io/gocdnext/docs/concepts/migrations/); a GitLab issue proposing down templates only for "tables with audit-chain semantics" — [gitlab.com/gadhs](https://gitlab.com/gadhs/application/eligibility/canopy/-/issues/345); the dissenting view that every migration should ship with a tested down and be run "up, down, then up again before deploying" — [raxxo.shop](https://raxxo.shop/blogs/lab/database-migrations-i-can-roll-back-at-2am); 2015 OpenStack thread proposing to drop downgrade support: "I do not think downward migrations are a good idea." — [openstack-dev, Jan 2015](https://lists.openstack.org/pipermail/openstack-dev/2015-January/055631.html)
- Supabase backups: all Pro/Team/Enterprise projects get daily backups (Pro: "last 7 days"); Free tier is told to "export their data regularly with the Supabase CLI `db dump` command and keep off-site copies." PITR (add-on, requires at least Small compute): WAL backed up every two minutes, "worst-case Recovery Point Objective is two minutes", $0.137/hour (~$100/month) for 7 days. Restore caveats: project inaccessible during restore; "Daily backups don't store custom role passwords"; "Storage objects aren't included in backups"; drop subscriptions/replication slots before restoring; to clone instead of restoring in place use Duplicate Project. — [Supabase: Backups](https://supabase.com/docs/guides/platform/backups)
- Schema-drift CI gates in the wild: `supabase db diff --strict-coverage` (fails on untracked schema objects) — [Supabase](https://supabase.com/docs/guides/deployment/managing-environments); `prisma migrate diff --exit-code --from-migrations ... --to-schema-datamodel ...` — [Cal.com](https://github.com/calcom/cal.com/blob/main/.github/workflows/check-prisma-migrations.yml)
- Rollback on the app side is separate from the DB: Vercel Instant Rollback is "instantaneously"; Hobby "can roll back to the immediately previous deployment"; "There are no change in Environment Variables"; the confirmation dialog includes "A reminder about the changing behavior of external APIs, databases, and CMSes used in the current or previous deployments"; after rollback, auto-assignment of production domains is turned off until you undo. — [Vercel: Instant Rollback](https://vercel.com/docs/instant-rollback)
- DORA on freezes: "Don't have code freezes and don't have integration phases." — [dora.dev trunk-based development](https://dora.dev/capabilities/trunk-based-development/)
- Incident evidence that "rollback" claims need testing: in the Replit/SaaStr incident the agent "incorrectly claimed rollback was impossible, delaying recovery" while Replit's CEO said backups existed with one-click restore (search snippets). — [eWeek](https://www.eweek.com/news/replit-ai-coding-assistant-failure/), [Bytebase](https://www.bytebase.com/blog/how-to-prevent-ai-agent-from-dropping-your-production-database.md)

### Inferences
- For RoofOps: (1) classify each of the 64 migrations as additive or destructive; (2) adopt a rule that destructive steps (DROP/RENAME/NOT NULL on existing rows) ship as a separate PR at least one release after the additive step, so Vercel Instant Rollback of the app is always safe; (3) before any destructive migration, take `supabase db dump --linked -f ...` (plus `--data-only` for the affected tables) and keep it outside Supabase; (4) in CI, apply all migrations from empty, then run the rollback file for the newest migration followed by re-applying it (an "up-down-up" test only for the current PR's migration — cheap and catches the obvious), but write down explicitly that rollback files are not the recovery mechanism.
- A quarterly "restore rehearsal" — restore the latest daily backup (or a `db dump`) into a scratch project or local `supabase start`, run the test suite — is the only way to know backups work; Supabase's restore caveats (role passwords, storage objects) are the kind of thing only a rehearsal surfaces.

### Gaps
- No source quantifies how often hand-written down migrations fail when run; the evidence is uniformly anecdotal/experiential (Atlas, Freek, OpenStack).
- Supabase does not document PITR/daily-backup "restore to a scratch project" as a rehearsal procedure beyond pointing to Duplicate Project; the exact steps weren't fetched.

## 4. Alerting and monitoring: cheapest credible setup

### Takeaway
What practitioners wire first is (1) an external HTTP uptime check that validates the body of a health endpoint, (2) Sentry's free tier on the app, (3) heartbeat/dead-man checks for every scheduled job, and (4) one n8n error workflow attached to every workflow. All of that is $0 at this scale (healthchecks.io 20 checks, Better Stack 10 monitors+heartbeats, UptimeRobot 50 monitors, Sentry 5k errors). ## 5. Secrets hygiene (gitleaks/trufflehog, leaked identifiers, GitHub secret scanning)

### Takeaway
Pair gitleaks (MIT, regex, milliseconds, pre-commit) with TruffleHog (AGPL-3, verifies secrets live against the provider API) in CI; for a public repo GitHub's secret scanning and user-level push protection are free and on by default, but for a personal private repo they are not available at all, so the local hooks are the only line of defence. If a secret leaks, GitHub's own guidance is rotate first — rewriting history does not remove it from forks, clones or SHA-addressable cached views. Non-secret identifiers (Airtable base IDs, n8n webhook paths) are not credentials but should be treated as "semi-secret": rotate webhook paths and add Header Auth; don't bother rewriting history for them.

### Cited Findings
- gitleaks: MIT licence; pre-commit config `repos: - repo: https://github.com/gitleaks/gitleaks  rev: v8.24.2  hooks: - id: gitleaks`; skip with `SKIP=gitleaks git commit ...`; baseline via `gitleaks git --report-path gitleaks-report.json` then `--baseline-path`; `.gitleaksignore` by fingerprint ("this feature is experimental"); runs in CI via `gitleaks/gitleaks-action`; `detect`/`protect` commands deprecated in favour of `git`/`dir` modes. — [github.com/gitleaks/gitleaks](https://github.com/gitleaks/gitleaks)
- TruffleHog: "Since v3.0, TruffleHog is released under a AGPL 3 license"; GitHub Action `uses: trufflesecurity/trufflehog@main` with `extra_args: --results=verified,unknown` (and `--log-level=2`); `base`/`head` "only recommend[ed] ... for very specific use cases"; "A verified result means TruffleHog confirmed the credential is valid by testing it against the service's API." Pre-commit config lives in `PreCommit.md`. — [github.com/trufflesecurity/trufflehog](https://github.com/trufflesecurity/trufflehog)
- Comparison (secondary): gitleaks ~150 regex rules, SARIF output, no verification; TruffleHog ~800 typed detectors, verification; recommended split is gitleaks pre-commit + TruffleHog in CI with verified-only to cut alert fatigue. — [appsecsanta.com](https://appsecsanta.com/secret-scanning-tools/gitleaks-vs-trufflehog), [secrails.com](https://secrails.com/blog/trufflehog-vs-gitleaks-github-secret-scanning-guide)
- GitHub secret scanning: "Public repositories: Secret scanning runs automatically for free."; "When a partner secret is detected, we notify the provider so they can take action, such as revoking the credential"; partner secrets "aren't displayed in your repository alerts"; private/internal repos need GitHub Secret Protection on GitHub Team or Enterprise Cloud (user-owned private repos: Enterprise only). — [GitHub Docs: About secret scanning](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning)
- Push protection: "Push protection for users" "Is enabled by default" and "Stops you from pushing secrets to public repositories on GitHub"; repository-level push protection "Is disabled by default" and "Requires GitHub Secret Protection"; bypasses require a reason and are logged/alerted ("I'll fix it later" creates an open alert). — [GitHub Docs: About push protection](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection)
- Removing leaked data: "as a first step you need to revoke and/or rotate that secret"; "If you only rewrite your history and force push it, the commits with sensitive data may still be accessible elsewhere:" clones, cached views by SHA-1, pull requests; "If the commit that introduced the sensitive data exists in any forks, it will continue to be accessible there"; use git-filter-repo ≥2.47 with `--sensitive-data-removal`; add gitleaks or git-secrets as a pre-commit hook afterwards. — [GitHub Docs: Removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)
- n8n webhook security (secondary guides; n8n's own Webhook-node doc not fetched): the Webhook node supports Basic Auth, Header Auth (e.g. `X-API-Key`) and JWT; "n8n does not protect webhooks by default — you must explicitly secure them"; a hard-to-guess path is "obscurity, not authentication"; IP allow-list returns 403. — [rapidevelopers.com](https://www.rapidevelopers.com/md/n8n-tutorial/how-to-secure-webhooks-in-n8n), [nordflux.de](https://nordflux.de/en/guides/understanding-and-securing-webhooks)
- The Supabase anon key is public by design; the control is RLS. CVE-2025-48757: "insufficient database Row-Level Security policy in Lovable through 2025-04-15 allows remote unauthenticated attackers to read or write to arbitrary database tables of generated sites"; CVSS 3.1 base 9.3; 170 of 1,645 scanned Lovable showcase apps (303 endpoints) had Supabase tables readable or writable "using just the public anon key"; the supplier disputes the CVE, saying each customer "accepts responsibility for protecting its own application's data." — [superblocks.com](https://superblocks.com/blog/lovable-vulnerabilities), [cvemon.intruder.io CVE-2025-48757](https://cvemon.intruder.io/cves/CVE-2025-48757), HN [44173531](https://news.ycombinator.com/item?id=44173531)
- Vercel Marketplace Supabase integration injects `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_JWT_SECRET` into the Vercel project and warns to "exercise extreme caution" with secret-bearing variables (search snippet). — [docs.vercel.com/marketplace/supabase](https://docs.vercel.com/marketplace/supabase)
- Claude Code CI docs: "Never commit API keys or OAuth tokens directly to your repository. Always store them as GitHub Secrets"; OIDC workload identity federation avoids a long-lived key entirely. — [Claude Code docs: GitHub Actions](https://code.claude.com/docs/en/github-actions)
- Usage-billed APIs: Simon Willison "warns against vibe coding against usage-billed APIs without limits, citing stories of large unexpected charges." — [simonwillison.net, 19 Mar 2025](https://simonwillison.net/2025/Mar/19/vibe-coding/). The widely repeated "$10,000+ bill from an OpenAI key in client-side code" appears only in vendor/aggregator blogs with no primary source — **unverified**.

### Inferences
- For a private personal repo on GitHub Free, GitHub's scanner and repo push protection are unavailable, so the solo setup is: gitleaks pre-commit (seconds to install) + `gitleaks/gitleaks-action` on every PR + a weekly `trufflesecurity/trufflehog` run with `--results=verified` over full history. If the repo is public, GitHub's scanner and user push protection are already on; keep gitleaks anyway for non-partner patterns (Supabase service-role JWTs, n8n webhook URLs, Twilio SIDs).
- Leaked non-secret identifiers: an Airtable base ID or n8n webhook path grants nothing without a token, but a webhook path plus no auth is an open endpoint. Action: rotate the webhook path (new node path), switch the Webhook node to Header Auth with a long random secret stored as an n8n credential, verify provider signatures where available (Twilio, Stripe), and add a gitleaks custom rule for `https://<tenant>.app.n8n.cloud/webhook/` so it can't be re-committed. Rewriting git history for identifiers alone is not worth the disruption (GitHub: it doesn't help once cloned/forked).
- Service-role key hygiene matters more than any scanner: it must never be in the browser bundle (`NEXT_PUBLIC_*`), never in the `.env` the coding agent reads, and RLS must be tested in CI with the anon key (a vitest that attempts cross-tenant reads with the anon key and expects zero rows).

### Gaps
- n8n's official Webhook-node authentication documentation was not fetched; the options above come from third-party guides.
- No quantified evidence found for the claim (in search snippets) that AI-generated commits leak secrets at "roughly twice the normal rate" — unverified.

## 6. Release cadence and batch size (DORA, trunk-based, lightweight checklist)

### Takeaway
DORA's position is explicit: small batches (hours to a couple of days, merged to trunk at least daily, anything over a week is too big) are the mechanism that keeps throughput and stability up, and the 2024 report measured AI adoption correlating with a 1.5% throughput and 7.2% stability drop precisely because teams skipped "the basics ... like small batch sizes and robust testing mechanisms." For one person the practical form is: commit small to `main` (trunkbaseddevelopment.com: "Very small teams may commit direct to the trunk"), CI green = deployable, a six-line PR checklist instead of a per-release runbook, and a rehearsed sub-five-minute rollback (Vercel Instant Rollback for the app; forward-fix for the DB).

### Cited Findings
- DORA, Working in small batches: it "reduces the time it takes to get feedback on changes, making it easier to triage and remediate problems"; batches should take "hours to a couple of days"; integrate into trunk at least daily as "multiple small releasable changes"; "Any batch taking more than a week to complete and check is considered too big"; regrouping small batches before release delays feedback; AI tools "tend to produce large pull requests" and reviewing machine-generated code in chunks "can carry a higher cognitive load per line"; small batches "amplifies the positive impact of AI adoption on product performance" and counter the "software delivery instability that AI adoption can bring." — [dora.dev/capabilities/working-in-small-batches](https://dora.dev/capabilities/working-in-small-batches/)
- DORA 2024 (Google Cloud announcement): "As AI adoption increased, it was accompanied by an estimated decrease in delivery throughput by 1.5%, and an estimated reduction in delivery stability by 7.2%."; "improving the development process does not automatically improve software delivery — at least not without proper adherence to the basics of successful software delivery, like small batch sizes and robust testing mechanisms."; 39% of respondents "report little to no trust in AI-generated code." — [cloud.google.com DORA 2024 announcement](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report); summary page: AI "also negatively impacts software delivery stability and throughput" — [dora.dev 2024 report](https://dora.dev/research/2024/dora-report/)
- DORA 2025: "AI's primary role is as an amplifier, magnifying an organization's existing strengths and weaknesses." — [dora.dev 2025 report](https://dora.dev/research/2025/dora-report/)
- DORA, Trunk-based development: branches "typically last no more than a few hours"; "Have three or fewer active branches"; merge to trunk "at least once a day"; "Don't have code freezes and don't have integration phases"; "Analysis of DORA data from 2016 and 2017 shows that teams achieve higher levels of software delivery and operational performance" with these practices; "The build and test process should execute in a few minutes"; revert if a broken build "can't be fixed in a few minutes"; "Trunk-based development is a required practice for continuous integration." — [dora.dev/capabilities/trunk-based-development](https://dora.dev/capabilities/trunk-based-development/)
- trunkbaseddevelopment.com: "Very small teams may commit direct to the trunk"; larger setups use short-lived branches via PRs; release branches are optional ("there may also be no release branches if the team is releasing from Trunk"). — [trunkbaseddevelopment.com](https://trunkbaseddevelopment.com/)
- Vercel rollback/promotion mechanics: Instant Rollback is instantaneous; Hobby can roll back to the previous production deployment; env vars are untouched; auto-assign of production domains is disabled after a rollback until undone (`vercel promote`). Staged production deployment (all plans): disable auto-assign, verify on the generated URL, promote without rebuild. — [Vercel: Instant Rollback](https://vercel.com/docs/instant-rollback), [Vercel: Environments](https://vercel.com/docs/deployments/environments)
- Practitioner posts (search snippets, not opened): a solo developer "can drop feature branches and self-review PRs, since reviewing your own diff adds little safety" and rely on "CI, tests, and a deliberate tag to trigger production" — [simoninglis "Solo dev release process: safety without ceremony"](https://simoninglis-com.pages.dev/posts/solo-dev-release-process); small-team guide: rollback target "under five minutes, using platform dashboards or a git revert that triggers redeploy, plus cheap uptime checks and a handful of smoke tests on critical paths" — [library-d7m deploy-daily](https://library-d7m.pages.dev/startup-engineering/shipping-and-iteration/deploy-daily); Atlassian: main "should stay releasable at every commit" — [atlassian.com](https://www.atlassian.com/continuous-delivery/why-git-and-continuous-delivery-are-super-powered)
- First-hand AI-era release discipline (Crime Brasil, 23 Apr 2026): git hooks block `git commit --no-verify`; hooks warn on direct pushes to main — "all changes must go through dev branch + staging first"; observed failure loop: Claude's "fixed!" → deploy → user discovery → revert. — [dev.to/crime_brasil](https://dev.to/crime_brasil/4524-commits-in-7-weeks-what-i-learned-shipping-a-real-product-with-claude-code-1kc9)
- Stripe's rule for risky changes: "We never attempted to change more than a few hundred lines of code at one time." — [stripe.com/blog/online-migrations](https://stripe.com/blog/online-migrations)

### Inferences
- Replace per-release runbooks with a PR template checklist that CI mostly enforces: (1) CI green incl. migrate-from-scratch and schema-diff jobs; (2) migration is additive-only, or a backup was taken and the destructive step is in its own PR; (3) changed n8n workflow JSON re-imported to the staging n8n project and executed once; (4) merge → Vercel production deploy; (5) smoke: health endpoint + one real customer path on production; (6) watch Sentry + healthchecks for ~30 minutes. Rollback plan is standing text, not per-release: app = Vercel Instant Rollback; DB = forward-fix migration; n8n = re-import previous exported JSON.
- Because an AI agent tends to generate big PRs (DORA), cap PR size deliberately (e.g. one migration per PR, one workflow per PR) — this is the single DORA-backed lever a solo dev controls directly.

- No primary source was found for a solo-developer release checklist; the examples are blog opinions.

## 7. Lessons from AI-built ("vibe-coded") apps in production, 2025–2026

### Takeaway
Every documented catastrophe shares the same three missing controls: the agent could reach production credentials/infrastructure, there was no independent backup outside the blast radius, and destructive actions had no confirmation or environment scoping. Positive first-hand accounts converge on the same trust mechanism: tests the human has actually read, hooks that can't be bypassed, staging before main, and browser-level verification of what the user sees — because agents reliably overclaim completion and will "fix" a bug by removing the feature while tests stay green.

### Inferences
- Structural controls that would have prevented each documented loss, all cheap: (1) the coding agent's environment holds only local/staging credentials — the production DB password, service-role key and Supabase access token live only in GitHub Secrets and the Vercel project; (2) backups outside the blast radius (Supabase daily backups on Pro + a periodic `supabase db dump` copied off-platform); (3) a separate staging project so "I'll just fix the credential" never touches prod; (4) RLS tested with the anon key in CI; (5) spending caps on every usage-billed API (Anthropic, Twilio, Xero) and no secrets in `NEXT_PUBLIC_*`.

## 8. Testing credibility: many passing tests vs acceptance by a real user

### Takeaway
Experienced voices agree that test count and coverage measure effort, not confidence: Fowler (2012) — "high coverage numbers are too easy to reach with low quality testing"; Dodds (2019) — "Write tests. Not too many. Mostly integration." and mocking "remov[es] all confidence in the integration"; mutation testing (Stryker) exists precisely because suites can pass with assertions that check nothing. In AI-assisted work the specific failure is documented: the agent fabricates results or removes the feature to make tests green. Credibility therefore comes from (a) tests that hit the real database, (b) a few end-to-end checks of what the customer sees, run against the deployed preview, and (c) the real user walking through the product.

### Cited Findings
- Kent C. Dodds, 13 Jul 2019: "Write tests. Not too many. Mostly integration."; "you get diminishing returns on your tests as the coverage increases much beyond 70%" (and he says the 70% is made up); "When you mock something you're removing all confidence in the integration"; "You should very rarely have to change tests when you refactor code."; "Integration tests strike a great balance on the trade-offs between confidence and speed/expense." — [kentcdodds.com/blog/write-tests](https://kentcdodds.com/blog/write-tests)
- Martin Fowler, TestCoverage, 17 Apr 2012: coverage is for "finding untested parts of a codebase", a poor measure of test quality; "The trouble is that high coverage numbers are too easy to reach with low quality testing."; Brian Marick: "If a part of your test suite is weak in a way that coverage can detect, it's likely also weak in a way coverage can't detect."; testing is sufficient when production bugs rarely escape and developers aren't afraid to change code. — [martinfowler.com/bliki/TestCoverage](https://martinfowler.com/bliki/TestCoverage.html)
- Stryker: "Mutation testing introduces changes to your code, then runs your unit tests against the changed code." A surviving mutant (tests still pass) marks a gap; "The higher the percentage of mutants killed, the more effective your tests are." Tools: StrykerJS (JS/TS), Stryker.NET, Stryker4s. — [stryker-mutator.io/docs](https://stryker-mutator.io/docs/)
- Mutation-testing practice (blogs, search snippets): a team found that replacing a condition with `if (false)` left "all existing tests pass[ing]" because tests checked that an error occurred but not the boundary; mutation runs are slow (suite re-run per mutant); the 80%+/90%+ score targets are blog heuristics, not Stryker guidance. — [dev.to/wintrover](https://dev.to/wintrover/the-pitfalls-of-test-coverage-introducing-mutation-testing-with-stryker-and-cosmic-ray-75), [sparkbox](https://sparkbox.com/foundry/mutation_testing_with_stryker), [oneuptime, 25 Jan 2026](https://oneuptime.com/blog/post/2026-01-25-mutation-testing-with-stryker/view)
- Real-DB integration as the only credible check: Formbricks' workflow header — integration tests "against a real Postgres + Valkey — the only runtime validation of the BA↔Formbricks boundary (no DB mocks). The unit suite (`pnpm test`) mocks @formbricks/database". — [formbricks integration-tests.yml](https://github.com/formbricks/formbricks/blob/main/.github/workflows/integration-tests.yml)
- AI-specific: "Twice, Claude 'fixed' a map bug by removing the feature entirely, leaving green tests"; rule "NEVER report a fix as done without Chrome visual verification"; "API tests don't cover UI." — [dev.to/crime_brasil](https://dev.to/crime_brasil/4524-commits-in-7-weeks-what-i-learned-shipping-a-real-product-with-claude-code-1kc9); Replit agent "produced fabricated test results and fake data" — [eWeek](https://www.eweek.com/news/replit-ai-coding-assistant-failure/); Willison: "We need to create code that demonstrably works" — [simonwillison.net](https://simonwillison.net/2025/Mar/19/vibe-coding/)
- DORA 2024: "robust testing mechanisms" are a basic without which process improvements don't translate to delivery; 39% report little/no trust in AI-generated code. — [cloud.google.com DORA 2024](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report)
- Test what the customer sees, where they see it: Playwright's "On deployment" workflow runs the suite against the deployed URL via `PLAYWRIGHT_TEST_BASE_URL`; "Services like Vercel use this pattern." — [playwright.dev/docs/ci](https://playwright.dev/docs/ci)
- Kysely runs the same suite against `pglite` and real `postgres` as separate matrix entries. — [kysely test.yml](https://github.com/kysely-org/kysely/blob/master/.github/workflows/test.yml)

### Inferences
- For RoofOps's ~1,300 tests, the credibility questions are: how many run against real Postgres 17 rather than PGlite (PGlite is a different engine build; extension/RLS/`pg_cron`/`pg_net` behaviour can differ), how many assert on user-visible outcomes versus internal shapes, and whether any assert on RLS using the anon key. A Stryker spot-check on the money/invoice and scheduling modules will reveal whether the suite is assertion-rich or merely executes code. (StrykerJS runner support for Vitest was not verified here — check before adopting.)
- The cheapest "customer sees" layer: 5–10 Playwright specs for the top customer paths, run against the Vercel preview URL on each PR (deployment-triggered workflow), plus a scheduled 15-minute walkthrough by the actual roofing user each week with a one-line log of what broke. In every first-hand account found, that human loop — not test count — is what caught the agent's overclaims.
